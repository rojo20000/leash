## README section
Insert `## Human front end: Clinic Assistant` immediately before `## Results` in `README.md`. Plain, short (about
10-15 lines), the repo's tone (read the neighbouring sections first). It must say:
- What it is: Clinic Assistant (`clinic-assistant/`), a clinician-facing app by Sal Jimenez, Python standard library
  only, served on `http://127.0.0.1:8642`, local model through Ollama or a stand-in with `MOCK_LLM=1`; see
  `clinic-assistant/README.md` for its own setup (accounts via `python manage_users.py add <name> clinician`).
- Integrated mode: when on, a signed-in clinician, nurse or clinical lead can search Leash's synthetic patients and
  open one through the Leash gateway (`POST /v1/tool-call`) from a "Leash" tab. Each request carries a request id
  (`call_id`) that appears in both Clinic Assistant's audit log and Leash's decision feed and audit log.
- It is **off by default** (`leash.enabled: false` in `clinic-assistant/config/policy.json`). Switch it on for one run
  without editing the file: start the Leash stack with `make dashboard`, then
  `cd clinic-assistant && CLINIC_LEASH=1 MOCK_LLM=1 python run.py`.
- The four outcomes: allowed (minimized record plus what Leash removed), blocked (reason codes plus Leash's advisory
  explanation), waiting for review in Leash (approve or deny in the dashboard at `http://127.0.0.1:8501`), and gateway
  unreachable (an error; Clinic Assistant never falls back to its own records).
- The honest limit: Leash's prototype enforces a single `scheduling_assistant` policy, so every Clinic Assistant role
  is sent as that role. The scheduling view (Patient, Encounter, DocumentReference) is allowed; a full-chart request
  (adding Condition and MedicationRequest) is blocked by design. A per-role clinician policy is future work.
- Tests: `make clinic-check` runs Clinic Assistant's own suite with the stand-in model; it is outside `make check`.
